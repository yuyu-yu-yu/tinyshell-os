## 成员 D（系统状态、真实交互测试、答辩交付）

### D1. Docker 如何保证四人的构建环境一致？

仓库根目录 `Dockerfile` 固定 Ubuntu 24.04 镜像摘要和软件包列表（GCC、32 位支持、GRUB、QEMU、Python 3 等）。所有提交和 PR 以容器内 `make test` 为准，宿主机编译只作快速反馈。禁止为通过测试而临时安装未写入 Dockerfile 的包；缺依赖应在 PR 中说明，由约定角色统一改镜像。GitHub Actions 使用同一 Dockerfile 再跑一遍，避免“我机器能过”。

### D2. 为什么 QEMU `sendkey` 比直接调用 keyboard handler 更能证明 IRQ1 链路？

`keyboard_feed_scancode()` 或直接 `shell_runtime_handle_char()` 只证明 C 函数本身。`sendkey` 让 QEMU 注入虚拟 PS/2 事件，经过 PIC → IRQ1 stub → `keyboard_handle_irq` → 有界队列 → 前台 `keyboard_pop_char` → 行编辑/命令。这才能证明中断路径和节流（hold 5 ms、间隔 20 ms）在真实 IRQ 下不会打满 64 字节队列。Day 2 禁止用直接调 parser 冒充该测试。

### D3. 启动 marker 测试与真实交互测试分别能证明什么？

启动矩阵（16/64/128 MiB）证明：Multiboot 镜像合法、各模块自检标记各一次、`BOOT_OK` 一次、无 `BOOT_FAIL`/`PAGE_FAULT`、空闲页随内存递增。它在 `sti` 后只跑固定自检，不覆盖多命令行编辑。交互测试证明：提示符、回显、Backspace、RAMFS 读写追加删除、两次 `status` 计数前进、unknown command、`about` 含 Ring 0。两者缺一不可。

### D4. 为什么当前项目只能称为微内核原型？

微内核把策略性服务放到用户态。TinyShell 目前把 Shell 和 RAMFS 放在 Ring 0 内核里，没有 TSS、没有系统调用、没有用户地址空间、调度不抢占、IPC 不阻塞。已完成的是内核机制教学闭环，不是可隔离用户进程的完整微内核。答辩必须使用任务书中的原句口径。

## 成员 D 补充题（状态模块本身）

### D6. `system_status_read` 失败时为什么不能改调用者内存？

`status` 命令和启动自检都可能传入已有结构。NULL 或 `kheap_get_stats` 失败时若先写再返回 false，调用者会把半截计数打印出去。实现先填局部 `snapshot`，全部成功才赋值。这与 Multiboot/PMM 的“失败不改输出”同一纪律。

### D7. 为什么 ticks 和 IRQ0 不保证同一周期？

两次都是普通 `uint32_t` 读。采样中间可能发生 IRQ0，PIT handler 先加 tick，dispatcher 再加 `irq_count(0)`，顺序固定但快照仍可能切开。交互测试只要求第二次读数更大，不要求相等或原子成对。

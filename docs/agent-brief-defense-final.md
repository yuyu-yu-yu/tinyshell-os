# TinyShell OS 答辩前两天收口任务书

> 建议执行时间：2026 年 8 月 28–29 日。若实际开始时间不同，按 Day 1、Day 2 顺延。
> 目标：冻结可演示版本，生成答辩材料并完成两轮预演。
> 本阶段不安排第五轮功能开发，不新增 Ring 3、系统调用、抢占调度、磁盘驱动或 Shell 命令。

## 给四位成员和 Agent 的使用方法

组长把本文件完整发给 A、B、C、D。每位成员把文件交给自己的 Agent，并追加：

```text
我是 TinyShell OS 成员 X，X 是 A、B、C、D 中分配给我的角色。
请完整阅读《TinyShell OS 答辩前两天收口任务书》，只执行成员 X 的任务。
不得新增内核功能，不得替我填写真实组号、姓名、学号或贡献比例。
所有材料必须基于代码冻结后的 main 和本人亲自核对的事实；最终 tag 由组长在文档收口后统一创建。
完成后给我文件、验证证据、仍需本人处理的事项和五个口头问答答案。
```

Agent 可以整理文字、生成排版稿和执行测试，但四位成员必须亲自审阅本人模块、运行测试并能解释正常路径、两个失败边界和一个已知限制。

## 当前事实与冻结规则

- 第四轮模块、Runtime、RAMFS、Shell 和真实 IRQ1 测试已经进入 `integration/cycle-04`。
- 标准 Docker 测试覆盖 16/64/128 MiB，并在最后运行 64 MiB QEMU `sendkey`。
- Shell 与 RAMFS 仍运行在 Ring 0。答辩统一称“教学型微内核原型”，不得宣称已完成用户态隔离。
- PR #18 合入 `main` 且 main CI 成功后冻结内核代码，但此时还不能创建最终 tag。
- 冻结后只有阻断演示或材料事实的缺陷才能修改。任何 `kernel/`、`include/`、Makefile 或测试脚本修改都必须重新运行完整 Docker 和 CI。
- 正式 PDF、PPTX、视频、个人信息和 ZIP 放在仓库外，不提交到 Git。

唯一发布顺序：

1. PR #18 合入 `main`，等待 main CI 通过，冻结内核代码；
2. A/B/C/D 从该 main 补齐各自贡献、问答和答辩材料；
3. D 汇总材料并建立最终文档 PR；
4. 文档 PR 合入 `main`，等待新的 main CI 通过；
5. 组长在这个最终提交上创建 annotated tag，再生成 `源码托管链接.txt` 和提交包。

## 文件所有权

为避免四个 Agent 同时修改同一文件，先各自提交独立材料，再由 D 汇总。

| 成员 | 仓库内独占内容 | 仓库外独占内容 |
|---|---|---|
| A | `docs/defense/contributions/member-a.md` | `源码托管链接.txt`、最终 SHA/tag/CI 证据 |
| B | `docs/defense/contributions/member-b.md` | 正式项目文档 DOCX/PDF、PDF 检查表 |
| C | `docs/defense/contributions/member-c.md` | 正式 PPTX、架构图、测试截图、备用录像 |
| D | `docs/defense/contributions/member-d.md`、`docs/defense/*` 汇总文件 | 最终 ZIP、邮件草稿、材料总检查表 |

A/B/C 不直接同时编辑 `project-report.md`、`member-qa.md` 或 `slides-outline.md`。D 在收到三份成员材料后统一合并。真实信息由本人填写，D 和 Agent 不得猜测。

每份 `member-x.md` 必须包含：

1. 姓名、学号和角色占位，留给本人填写；
2. 一页本人模块说明；
3. 两处关键代码位置；
4. 本人亲自运行的命令和结果；
5. 正常路径、两个失败边界、一个已知限制；
6. 一个本人实际作出的设计决定；
7. 五个答辩问题及完整答案；
8. AI 辅助了什么、本人审阅和修改了什么。

## Day 1：冻结事实并补齐内容

### A：代码冻结、发布证据与现场主操作

- 完成 `finalize → integration/cycle-04 → main` 的合并门禁。
- 从干净目录运行 `tools/docker-test.ps1`，记录三档 PMM 页数、全部 marker 和 `QEMU shell interaction: PASS`。
- 保存代码冻结 main SHA 和 CI URL；等最终文档 PR 合入且新 CI 通过后，再创建 annotated tag，建议名称 `v0.4.0-defense`。
- 编写 `member-a.md`，覆盖 Multiboot、分页、Runtime 和内核接线。
- 编写仓库外 `源码托管链接.txt`：仓库 URL、不可变 SHA/tag、Docker 复现命令。
- 准备现场启动、QEMU 操作和日志回退方案。

### B：报告正文与 PDF 准备

- 编写 `member-b.md`，覆盖 GDT、PMM、启动堆和 RAMFS。
- 重点解释 RAMFS 非法名称、512/513 字节边界、失败写入为何不破坏旧内容。
- 核对项目报告是否包含环境搭建、设计目标、实现过程、问题与解决、测试、心得和已知限制。
- 建立正式 DOCX/PDF 排版稿；D 冻结 Markdown 后再生成最终 PDF。
- 完成 B 的五问五答和报告逐页检查清单。

### C：PPT、图表与演示素材

- 编写 `member-c.md`，覆盖 IDT/IRQ、任务调度、IPC 和命令解析器。
- 按 `slides-outline.md` 制作 10–12 页、16:9 的第一版 PPTX。
- 至少制作四张基于最终版本的图或截图：总体架构、启动路径、真实 IRQ1 Shell 链路、三档内存/CI 证据。
- 固定现场命令顺序，不临时增加命令或功能。
- 写 60–90 秒备用录像镜头表和故障切换点。

### D：事实统一、20 题与提交清单

- 编写 `member-d.md`，覆盖 Console、PIT/键盘、IPC、状态快照和自动测试。
- 汇总四份成员材料，补齐 `member-qa.md`，每人至少五题，总计至少二十题。
- 更新贡献表和 AI/来源表；只写四人确认过的事实。
- 清除报告中的旧 SHA、“待合入”“未开始”和已解决故障描述。
- 更新 5–7 分钟演示稿、提交清单和邮件草稿。
- 保留诚实边界：无 Ring 3、系统调用、用户地址空间、持久化磁盘文件系统和抢占调度。

Day 1 结束前，全组进行第一次预演：允许看稿，完整运行 Shell，控制在 6–7 分钟。记录超时、口径冲突和演示故障。

## 最终验收门槛

代码必须满足：

- `main` 与远端一致，main CI 绿色；
- 16/64/128 MiB 全部通过，PMM 页数严格递增；
- 五个第四轮 marker 各出现一次，`BOOT_OK` 只出现一次；
- 日志不含 `BOOT_FAIL:` 或 `PAGE_FAULT`；
- 真实 `sendkey` 完整输出 `QEMU shell interaction: PASS`；
- tag 指向经过 CI 的最终 main 提交。

材料必须满足：

- 报告有阅读导航且没有占位状态；
- 至少二十个完整答案，每人至少五题；
- 贡献和 AI 使用由本人确认；
- PDF 已逐页目视检查，PPTX 和备用录像可离线打开；
- `源码托管链接.txt` 包含仓库、SHA/tag 和复现命令；
- ZIP 解压复核通过。

全员必须能解释：

- 本人模块的正常路径、两个失败边界和一个限制；
- 为什么 IRQ1 只入队，不在中断中解析命令；
- 为什么 `BOOT_OK` 只能在全部自检后输出；
- 为什么当前只能称 Ring 0 教学型微内核原型；
- AI 如何参与，本人具体审阅、修改和测试了什么。
